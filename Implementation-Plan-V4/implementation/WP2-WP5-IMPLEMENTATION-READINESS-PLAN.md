## 2. REM-WP2.1 — Pure policy specification and implementation

### 2.1 Implementation boundary

REM-WP2.1 owns only the deterministic authorization decision function and its pure domain fixtures/tests. It does not own persistence, trusted identity construction, HTTP behavior, PostgreSQL serialization, or product-path BDD execution. Those are owned by REM-WP2.2–REM-WP2.5 and REM-WP1.6 as mapped below.

### 2.2 Frozen specification and implementation boundary

Create a versioned canonical action catalogue. For every action, record its stable action ID, structured parameters, resource type, owning command/route, Phase 1 scope, source requirement/invariant, and whether the policy function itself or a later orchestration layer owns the decision. Capacity type must be a typed parameter, never concatenated into an arbitrary action string. Unknown or malformed IDs/parameters must deny.

Define the Phase 1 policy input types with distinct fields for tenant ID, organization ID, cohort/delegated scope where applicable and authenticated user ID. Record person-identity conflict rules as Phase 2 carry-forward; do not add Phase 2 finding actions to the Phase 1 matrix.

Separate authorization from governance enforcement mode. Define exactly how `allow`, `deny`, `advise` and `allow_with_label` map to the normative advisory/warning/blocking meanings in `03`; state whether any warning acknowledgment is required and who may acknowledge it. HARD invariants always deny prohibited actions and cannot be overridden. If the normative sources do not determine a mapping, record the exact owner decision needed before freezing the matrix; do not infer a security allow from a governance warning.

The verifier compares the single canonical matrix against required actor classes, actions and boundary dimensions; it rejects absent, duplicate, unrecognized or source-less rows. ### REM-WP5.3 — Persisted sessions and forced change

Use opaque, hashed server-side session records with the accepted cookie, CSRF, Origin, idle/absolute lifetime, rotation, logout and forced-change allowlist. Password-change authorization derives the authenticated account and tenant from the persisted session; it checks current credential and forced-change state. It does not require appointments, capacities or delegation data. The graph has no REM-WP2.2 prerequisite for this task.

Authentication inputs are resolved by owner ruling D-14 (2026-11-17), recorded in `02-decision-register.md` §7.3 and `docs/phase1/AUTHENTICATION_CONTRACT.md`: 12 Unicode code points minimum, no composition rules, long passphrases, and account/source progressive throttling at five failures per rolling 15 minutes with 1/2/4/8/16/32-second delays capped at 32 seconds. The rule applies independently to account and trusted source; use the greater active delay. REM-WP5.2/REM-WP5.3 must implement and test this exact policy, not treat the resolved inputs as a blocker. The 12-code-point minimum is a deliberate deviation from NIST 800-63B-4's 15-character single-factor minimum; do not claim conformance for that dimension. Hash using Argon2id m=19 MiB, t=2, p=1 with unique salts and versioned parameters, benchmarked under expected load.

For REM-WP5.3 throttling, implement a PostgreSQL-backed attempt-event store shared by every API instance. Store keyed HMAC identities for dimensions (`account`, `trusted_source`), never plaintext account identifiers or addresses. In a transaction, acquire per-dimension bucket locks in stable `(dimension, keyed_identity)` order, expire completed failures at `failed_at <= now()-15 minutes`, calculate delay from prior failed events plus already-running provisional attempts (excluding this request), and reserve this attempt before credential verification. Finalize the reservation as a failure only when verification fails; remove it on success. A successful login clears all account failures/reservations for that account only; source failures/reservations are retained unless this request succeeded, in which case remove only this request's source reservation. Provisional reservations left by process crashes expire after 15 minutes. This conservative in-flight reservation rule closes concurrent bypass while ensuring successful attempts do not persist as failures. Unknown accounts use the same account-key derivation and response path, preventing account enumeration. Do not use process memory, fixed windows, delayed asynchronous counters, or a per-instance cache as authority. PostgreSQL integration tests must use at least two independent API instances/connections and barriers to prove no lost increments, exact boundary behavior, and the same delay calculation under concurrent requests; use an injected clock or controlled test clock so tests assert delay outcomes without sleeping for the real schedule. Store cleanup must be bounded and must not alter the rolling-window result.

### REM-WP2.4 — One authority-scope serialization contract

The earlier prose in this readiness plan that specified a competing identity/lock representation, a separate actor/tenant aggregate, person/shared-identity Phase 1 locks, or `FOR UPDATE` for protected readers is superseded. The sole normative technical specification is [`authority-scope-serialization-spec.md`](../../../evidence/phase1/wp2.4/authority-scope-serialization-spec.md), contract v1, together with [`AUTHORIZATION_CAPACITY_CONTRACT.md`](../../../docs/phase1/AUTHORIZATION_CAPACITY_CONTRACT.md) v3 and [`authority-dependency-inventory.json`](../../../evidence/phase1/authority-dependency-inventory.json) v2.

The reconciled model retains D-04's actor/tenant aggregate as the single `actor_tenant` row in `symphony.authority_scope_versions`; no parallel aggregate-version store exists. The business command-target aggregate lock is separate and acquired first. Authority locks then follow exactly `global_policy → organization → tenant → actor_tenant → actor`, sorting each rank by `COALESCE(tenant_id::text, '') COLLATE "C"` and then `scope_id::text COLLATE "C"`. Database identity is the tuple `(scope_type, tenant_id, scope_id)` with PostgreSQL 18 `UNIQUE NULLS NOT DISTINCT`. Protected commands use `FOR SHARE`; source-changing authority commands use `FOR UPDATE`. Before locking, `symphony_app` may ensure only tenant/organization/actor_tenant rows under the tenant RLS policy; the bootstrap migration seeds the fixed global-policy row and required actor rows, which runtime verifies and treats as fail-closed if missing. Provision rows in canonical order, then acquire the complete lock set in canonical order. Person/shared-identity is Phase 2 only. A protected reader never increments authority versions; a source mutation increments each changed scope once in the same transaction.

Frozen Phase 1 source writers are tenant membership/assignment, platform roles/catalogue, appointments/source status, organization/cohort reassignment, and policy/configuration. PostgreSQL revokes app-role DML on those sources; startup/registry validation rejects mutation routes. Capacity and delegation grant/revoke are the only supported Phase 1 authority mutation families; they are specified by WP2.3 and each affected organization, tenant, and actor_tenant row is locked and versioned by REM-WP2.4.
