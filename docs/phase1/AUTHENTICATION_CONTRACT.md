# Phase 1 authentication and session policy contract

**Contract:** `phase1-authentication-v2`
**Status:** Owner-approved security baseline (approval assumed at user direction, 2026-11-07); the existing domain credential policy now rejects exactly at the 72-hour boundary. Persistent session/API behavior remains assigned to REM-WP5.
**Authority:** `03-specification-delta.md` §3.1 and ENR-010; ADR-005/018; Phase 1 REM-WP0.8/REM-WP0.10; existing auth tests are implementation evidence only, not policy approval.

| Policy item | Approved behavior | Implementation and verification gate |
|---|---|---|
| Temporary credential lifetime | 72 hours from server-side issuance, as approved under D-08 | No runtime/configuration override. Any future change requires a decision-register ruling and contract revision. Boundary tests at just-before, exactly-at, just-after. |
| Credential use | Single use, forced password change; source `03` §3.1/ENR-010 | Preserve source behavior and audit without recording plaintext |
| Session transport/cookie attributes | Opaque server-side session; no bearer token in browser local storage. Cookie `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`; HTTPS outside local development. | Implement as stated; prove cookie/TLS behavior in browser and API tests |
| Origin and CSRF | Synchronizer token plus Origin validation for state-changing requests | Implement exact policy and negative origin/token tests |
| Logout and session rotation | Create/rotate on login and privilege/tenant changes; logout revokes current session | Prove prior session unusable after each rotation/revocation |
| Forced-change route allowlist | Only password change, logout, session/CSRF support, and essential authentication endpoints before change succeeds | Enumerate exact endpoints; deny all others through API composition |
| Password policy | D-14 (2026-11-17): minimum 12 Unicode code points; accept spaces, Unicode and passphrases; no composition rules; maximum 1024 code points as an input/KDF resource bound; never trim, normalize, truncate or partially verify. Reject locally against a versioned common/compromised-password blocklist; never transmit a candidate password to an external lookup service. This project-approved 12-character minimum is below NIST SP 800-63B-4's 15-character SHALL for single-factor passwords; do not claim NIST conformance for this dimension. | Test boundaries at 11/12/1024/1025 code points, Unicode and spaces, full-input verification, no normalization/truncation, blocklist denial and secret redaction. |
| Password hashing | Use Argon2id, unique random salt per credential, m=19 MiB, t=2, p=1; store an encoded/versioned hash with parameters. Benchmark under expected server load and keep one verification under one second. Rehash on successful authentication when the stored scheme/parameters are below the current version. | PostgreSQL/API tests prove salted hashes differ for same input, verify full passphrases, and never persist/return/log plaintext. Parameter migration/rehash must be explicit and backward compatible. |
| Brute-force/rate limits | D-14: maintain account and trusted-source failure windows of 15 minutes. First five failures in a window have no added delay; on a request after five prior failures, impose 1, 2, 4, 8, 16, then 32 seconds, capped at 32 seconds. Compute account/source delays independently and apply the greater delay, not their sum. Apply delay before credential verification regardless of whether the account exists; use generic failure responses. Each failure expires exactly 15 minutes after occurrence. Successful authentication clears only that account's failure history; source history expires by its own window. There is no permanent lockout. | Use a shared PostgreSQL-backed event store across API instances. Reserve an expiring provisional attempt under per-account/source locks before verification, calculate delay from prior failures plus already-running reservations (excluding the current reservation), and atomically finalize reservations as failed or remove them on success. This closes concurrent bypass without treating successful attempts as lasting failures; abandoned reservations expire after 15 minutes and cannot cause permanent lockout. Expire failure events exactly at the 15-minute boundary. Store keyed HMAC identifiers, not raw login identifiers or IP addresses. Resolve source from the socket or explicitly trusted proxy configuration, never an arbitrary forwarding header. Test threshold, each delay step/cap, exact rolling expiry, independent and combined account/source behavior, success reset, provisional cleanup/crash expiry, parallel requests across two API instances and generic responses. |
| Idle and absolute session lifetime | 30-minute idle; 12-hour absolute; no “remember me” bypass | Boundary tests immediately before/at/after each limit |
| Password change revocation | Revoke every existing session, including the session performing the password change, and require a fresh login. Do not rotate the current session into a continuing authenticated session. | Multi-session API/browser test proves all old session IDs, including the submitting one, fail after commit and fresh login succeeds |
| Concurrent sessions | Multiple sessions permitted, each with independent revocation | Prove revoking one session does not revoke another except on password change |

Temporary credentials expire exactly 72 hours after server-side issuance, are single-use, and force password change. Session settings in this contract are owner-approved by direction of 2026-11-07. Password, hashing and rate-limit settings are approved by D-14 on 2026-11-17 and are no longer open owner inputs. The 12-code-point minimum is a deliberate project policy; this contract does not claim compliance with the stricter NIST single-factor minimum.

**REM-WP0.8 evidence:** `packages/domain/src/identity/__tests__/auth.test.ts` proves the 72-hour boundary with an injected clock. The first run failed at the exact boundary because `AuthService` used a strict `>` comparison; changing the expiry predicate to `now >= expiresAt` made all seven focused auth tests pass. The database-backed account/session lifecycle remains a REM-WP5 acceptance responsibility.

## REM-WP0.10 exact session policy and forced-change route contract

The forced-change session allowlist is exact and method-sensitive:

| Method/path | Unauthenticated use | Forced-change session | CSRF/Origin |
|---|---|---|---|
| `GET /auth/csrf` | Issues a pre-auth synchronizer token needed for login | Allowed; refreshes the session-bound token | Safe read; same-origin response policy |
| `POST /auth/login` | Public login using the shared `userId`, `credential`, `deviceId` body | Denied for an already authenticated forced-change session | Require configured Origin and pre-auth synchronizer token |
| `GET /auth/session` | Denied without a session | Allowed; returns only authentication/forced-change state and a session-bound CSRF token | Safe read |
| `POST /auth/change-password` | Denied | Allowed; authenticated actor is derived from session | Require synchronizer token and valid Origin |
| `POST /auth/logout` | Denied | Allowed; revokes only the current session | Require synchronizer token and valid Origin |
| `GET /health/live`, `GET /health/ready` | Infrastructure-only endpoints; return no user/session data | Not subject to user session policy | No business mutation |
| Every other application/API route | Session policy applies | Denied with the stable forced-change-required error; no business command is accepted | Unsafe methods require synchronizer token and valid Origin |

The `/auth/csrf` and `/auth/session` endpoints return the synchronizer token only to the same-origin browser context; responses use `Cache-Control: no-store, private`, CORS is disabled except an explicitly configured exact same-origin policy, and the session cookie is host-only (no `Domain` attribute). The browser holds the synchronizer token in memory and sends `X-CSRF-Token` on unsafe requests. Login rotates the pre-auth token into a new session-bound token. Successful password change revokes every session, including the submitting session, and requires a fresh login; it does not rotate that session into a continuing session. Privilege/tenant changes rotate the current session identifier and CSRF token. Logout revokes only the current session. Multiple concurrent sessions are permitted and independently revocable.

Session validity is `now < issued_at + 12 hours` **and** `now < last_activity_at + 30 minutes`; equality is expired. Temporary credential validity is `now < issued_at + 72 hours`; equality is expired. There is no remember-me override.

The accepted policy requires progressive delay by account and trusted source, generic failure responses, and no permanent account lockout. D-14 fixes the exact thresholds, delay schedule, window and reset behavior above. Implement this policy through a shared, concurrency-safe store; an in-process Map is not an acceptable rate-limit store for multiple API processes.
