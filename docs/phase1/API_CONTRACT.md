# Phase 1 shared HTTP/API contract

**Contract:** `phase1-http-api-v2`
**Status:** Owner-approved WP0 baseline (approval assumed at user direction, 2026-11-07); API/browser implementation and contract tests remain pending.  
**Authority:** Phase 1 remediation plan v2 §1, WP0.9/WP0.10/WP5; `03-specification-delta.md` §§3.1, 9; `04-architecture.md` §§3, 5; features 01/02/09/10; current route code is evidence of the mismatch, not normative authority.

## Rules shared by browser, API and command facade

1. `packages/contracts` is the single source of versioned request/response schemas and inferred TypeScript types. API validates untrusted input with Zod; the workspace imports the same contract. No duplicate hand-maintained DTOs or `as`-casts at an API boundary.
2. Authenticated actor, tenant, role, capacity, appointment and delegation context are resolved server-side. Client-supplied actor/tenant/role/approval/standing fields are rejected or ignored according to the command schema and never grant authority.
3. JSON objects are strict: unknown fields fail validation, defaults are materialized before semantic digest, and malformed/duplicate-key input is rejected before normal JSON parsing for command hashing.
4. Every response has a classified result/error code and a documented HTTP status. A validation error does not echo secrets or raw request bodies. Logs/events/receipts contain no credentials, tokens or raw member PII.
5. Logical `correlation_id` is not interchangeable with request/trace correlation. `recorded_at` is server generated. Command metadata semantics are those in `COMMAND_TRANSACTION_CONTRACT.md`.
6. Browser acceptance must use the actual workspace server, actual API composition and PostgreSQL-backed test user. It must not intercept/mock `/auth/login` or report static `page.setContent()` as a route/API pass.

## Authentication routes

The current API route accepts `POST /auth/login` JSON `{ userId, credential, deviceId }`; the current workspace sends `{ email, password }`. WP5 must remove that mismatch by making both sides consume one shared contract. The v1 login request preserves the API's source-compatible field names `userId`, `credential`, `deviceId`; the UI may label the field “Email or user ID” but serializes it as `userId`. Reject unknown fields and do not reflect field values in error output.

Login success returns `forcedChangeRequired` and establishes an opaque server-side session using an `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/` host-only cookie with no `Domain` attribute. HTTPS is required outside local development. Do not return a bearer session token in the JSON body, URL, or persistent browser storage. `/auth/csrf` and `/auth/session` responses use `Cache-Control: no-store, private`; CORS is disabled unless an exact configured same-origin policy is explicitly needed. State-changing requests require a synchronizer CSRF token and valid Origin. Rotate/create a session after login and on privilege or tenant change. Logout revokes the current session; password change revokes all sessions including the session making the change and requires fresh login. These WP0.10 values are owner-approved by direction of 2026-11-07. Login failure uses a stable typed error envelope; it must not reveal whether an account exists. Current detail text “No credential on file” is not the final external error contract.

`POST /auth/change-password` requires an authenticated session. The target user ID is derived from that session, never trusted from the body. The body contains only current credential proof if required by policy and the new password; it is strict and redacted in traces. Success atomically clears forced-change status, revokes all existing sessions, and requires a new login. Until forced change succeeds, only password change, logout, session/CSRF support, and essential authentication endpoints are allowed. The password policy and concrete bounded rate-limit algorithm must be sourced/recorded before WP5; do not invent a value or permanent lockout.

## Command API

The Phase 1 single-command route is `POST /commands`. It requires a valid persisted session, synchronizer CSRF token and valid Origin. A forced-password-change session is denied because `/commands` is outside the WP0.10 allowlist. Its strict v1 request body is `{ commandId: UUID, organizationId: UUID, occurredAt: RFC3339 timestamp, deviceId?: UTF-8 string of 1–128 bytes, expectedVersion: nonnegative safe integer | null, type: registered command discriminator, schemaVersion: registered version, payload: command-specific strict object }`. The route body limit is 1 MiB; malformed UTF-8, duplicate JSON keys, invalid Unicode, unknown fields, unknown command types and unregistered schema versions fail before command acceptance. `tenant_id` is the authorization/security boundary. `organizationId` is a distinct business target within that tenant; it is not an alias for the tenant ID. The server resolves and validates organization ownership in the command transaction. Include organization ID in semantic identity where it is not already represented in the validated command payload and where omitting it could make the same key refer to a different target. Each registered WP1 command payload declares exactly one UUID aggregate target; multi-aggregate commands are unsupported in WP1. The command registry declares whether `expectedVersion` must be a nonnegative safe integer (update) or `null` (creation/no-version precondition). `tenantId`, `actorUserId`, role/capacity/approval claims, `recordedAt`, and logical `correlationId` are not accepted body fields. Request/trace correlation is transport metadata and excluded from the semantic digest. Actor and tenant are derived from authenticated server context. Client `occurredAt` and `deviceId` are untrusted attribution assertions: neither controls event ordering, authorization, expiry nor retention. PostgreSQL `now()` is transaction-start time; any `recorded_at` based on it must be documented as transaction-start recording time, not exact request acceptance or commit time. The server constructs the internal `CommandEnvelope` with trusted fields and materializes schema defaults before canonicalization. The HTTP adapter and internal facade use shared versioned schemas and result unions from `packages/contracts`; no duplicate DTO is permitted.

For `POST /commands`, first successful commit returns HTTP 200. Same-actor replay of a successful receipt returns HTTP 200 with the same versioned safe result and `replayed: true`; this flag is transport metadata and does not alter the stored result. An accepted deterministic terminal `VERSION_CONFLICT` returns HTTP 409 on the first evaluation and on every replay. The replay has `replayed: true`, the same safe conflict body/result as the first response, and only the same opaque reconciliation ID; it does not re-evaluate the aggregate or create another inbox item. The initial conflict response has `replayed: false`. Wrong content type returns 415 `UNSUPPORTED_MEDIA_TYPE`; body over 1 MiB returns 413 `REQUEST_TOO_LARGE`; malformed JSON/UTF-8, duplicate keys or invalid Unicode returns 400 `INVALID_JSON`; valid JSON with invalid schema returns 400 `INVALID_COMMAND`. No response echoes raw input. Missing/invalid authentication returns 401 `UNAUTHENTICATED`; failed CSRF/Origin validation returns 403 `CSRF_REJECTED`; forced-password-change restriction returns 403 `FORCED_PASSWORD_CHANGE_REQUIRED`. Current authorization denial returns 403 `NOT_AUTHORIZED` with no business receipt. Same tenant/command ID with a changed actor or semantic envelope returns 409 `IDEMPOTENCY_KEY_REUSED` and never includes the prior result. Retryable transaction or required security-audit storage failure returns 503 `COMMAND_TEMPORARILY_UNAVAILABLE` with `retryable: true`, makes no claim of success/failure when commit is uncertain, and creates no denial receipt. The exact response schemas and discriminated union are defined once in `packages/contracts` and checked against these status rules.

Offline batch UI and batch replay execution are outside Phase 1. A future `POST /commands/batch` is a documented placeholder only; Phase 1 must not expose a loop that implies batch semantics. Its implementing work package must decide and test per-item transaction boundaries, ordering, partial failure, replay behavior and bounded request size before code is authorized. WP1.6 covers the single-command route/facade only. See `Implementation-Plan-V4/implementation/PHASE-1-REMEDIATION-PLAN-v2.md` §5 for the task-level schema, transaction and evidence gates.

The response distinguishes committed success, same-actor replay, deterministic terminal rejection (including stale conflict), retryable service/audit failure and non-disclosing key-reuse denial. Only committed safe results are replayable. A conflict may expose an opaque reconciliation reference, never raw preserved values. These result categories follow WP0.1; the Phase 1 remediation plan §5 fixes the HTTP schemas/status mapping, which is exported from `packages/contracts`. No response body can set a trusted status or authority.

The complete session/forced-change route allowlist, exact-expiry semantics, CSRF/Origin requirements and session-revocation rules are in [`AUTHENTICATION_CONTRACT.md`](AUTHENTICATION_CONTRACT.md) §WP0.10. The frozen forced-change allowlist is `GET /auth/csrf`, `GET /auth/session`, `POST /auth/change-password`, and `POST /auth/logout`; every other application/API route is denied. `POST /auth/login` remains public only for unauthenticated clients and cannot bypass a forced-change session restriction.

## Required contract tests

- API and workspace import the same schema/types; compile-time and runtime tests reject incompatible payloads.
- `userId/credential/deviceId` is the one login request representation; tests fail on an `email/password` duplicate DTO.
- Login response contains no credential and no session token in body; browser/API tests assert cookie attributes and CSRF/Origin behavior.
- Unauthenticated, invalid, forced-change, expired and revoked cases use the published status/code map; user-existence details are not disclosed.
- Change password cannot target another account by body field and cannot proceed without the permitted session state.
- Command actor/tenant/role are server-derived; forged client fields cannot authorize.
- Browser-to-API acceptance proves the API received and handled the request using server-side correlation evidence; no mocked login route.

The WP0.10 session values are approved. The command-route result/status contract above is fixed for WP1.6 and must be implemented in `packages/contracts`. Authentication route schemas must be made concrete there before WP5; password policy and the bounded rate-limit algorithm remain sourced implementation inputs, not permission to let API and UI drift or choose security values ad hoc.
