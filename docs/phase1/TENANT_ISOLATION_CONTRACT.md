Every persisted table is classified as `tenant_scoped`, `global_catalogue_read_only`, or `control_plane_restricted`. No table may remain unclassified. Every tenant table must have both `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY`. The accepted REM-WP0 baseline classified 53 tables; migrations 0010 and 0012 bring the current catalog to 55. The inventory, matrix, manifest and migration classify these as 37 tenant-scoped, 3 read-only global catalogues and 15 control-plane tables. The classification and candidate SQL are implemented; PostgreSQL catalog assertions in the restricted-role integration suite remain the verification gate.

The per-table privileges and tenant-resolution basis are recorded in `evidence/phase1/tenant-table-policy-matrix.json`; the 55-table catalog is recorded in `evidence/phase1/tenant-table-inventory.json`; and `evidence/phase1/wp1.5-tenant-policy-manifest.json` records each tenant SQL expression and parent path. The inventory's `rls_current` fields intentionally preserve the REM-WP0 baseline through migration 0012; the post-0013 effective policy and grant result is established by the candidate-pinned REM-WP1.5 CI evidence. Live DDL review found `requirement_sources` references global `requirement_definitions`, not `organization_requirements`; it is `control_plane_restricted` because its schema has no tenant path. `security_attempts` is tenant-scoped and INSERT-only for authenticated authorization denials with trusted actor/tenant context. `domain_events`, `command_receipts`, and `security_attempts` receive no UPDATE/DELETE grant; `reconciliation_inbox` is SELECT/INSERT/UPDATE only. `event_outbox` remains inaccessible directly to `symphony_app`; migration 0013 replaces direct inserts with a same-transaction function owned by NOLOGIN `symphony_outbox_writer`. FORCE RLS constrains that capability to pending inserts referencing an event in `app.tenant_id`; only `symphony_app` receives function EXECUTE, and PUBLIC does not. The restricted-role suite exercises this function through the actual transaction adapter.

The application role is a dedicated non-owner, non-superuser LOGIN role with no `BYPASSRLS`, DDL, memberships, or privileges beyond the matrix. CI provisions it ephemerally from `PHASE1_TEST_ADMIN_DATABASE_URL`, separate from migration and app URLs; application migrations do not create cluster roles. The local `symphony` database owner is never an application-role fallback. Runtime uses only transaction-local `app.tenant_id`, set with parameterized `set_config('app.tenant_id', tenant_id, true)` from authenticated server context. Historical migration 0008 remains unchanged; migration 0013 replaces its legacy policies. Missing/empty context and pooled reuse fail closed, and tenant queries retain explicit tenant predicates. The pool-reuse behavior is covered in the restricted-role integration suite.

Migration 0013 defines ENABLE+FORCE RLS and the full matrix. CI provisions an ephemeral migration role, app role, and outbox capability role; integration assertions check role attributes/memberships, effective table/function privileges, missing/empty context, cross-tenant reads/writes, catalog mutation denial, direct outbox denial, and pool reuse. These checks passed against PostgreSQL 18.0 under the dedicated actual application role in the run cited above. No RLS claim may be based only on a repository mock.

## Planned REM-WP2.4 authority-scope table

`symphony.authority_scope_versions` is a planned REM-WP2.4 control-plane table; it is not part of the current 55-table/0013 catalog and must not be described as already migrated. Its migration must add the table to `tenant-table-inventory.json`, `tenant-table-policy-matrix.json`, the applicable tenant-policy manifest, and migration catalog assertions in the same reviewed change. It must use `control_plane_restricted`, `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY`, with the exact tenant/actor/global policies and column grants in [`authority-scope-serialization-spec.md`](../../evidence/phase1/wp2.4/authority-scope-serialization-spec.md). The transaction must set both local `app.tenant_id` and `app.actor_user_id` from authenticated server context before resolver access. The actual app-role test must prove tenant and actor row visibility, denial of cross-tenant access, no direct delete/truncate, tuple-only inserts, version-only updates, and denial of writes to frozen global/actor rows. Capacity/delegation writes and increments must remain atomic; all frozen source DML stays revoked. These are future migration acceptance requirements and do not change the current WP1.5 result.
