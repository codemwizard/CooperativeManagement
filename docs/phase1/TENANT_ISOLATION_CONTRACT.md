# Phase 1 tenant isolation and application role contract

**Contract:** `phase1-tenant-isolation-v1`  
**Status:** Strict RLS direction owner-approved (approval assumed at user direction, 2026-11-07); table-by-table grant/policy evidence and PostgreSQL role proof remain pending.
**Authority:** ADR-005/022; AUD-004; INV-001; Phase 1 plan WP0.3; Phase 0 migration/role conventions.

Every persisted table must be classified before tenant policy work as one of: `tenant_scoped` (tenant key required, RLS enabled and forced, tenant context set per transaction), `global_catalogue_read_only` (no tenant key; application role SELECT only), or `control_plane_restricted` (explicit operation-specific grants, unavailable to ordinary application queries). No table may remain unclassified. Every `tenant_scoped` table requires both `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY`. `evidence/phase1/tenant-table-inventory.json` classifies all 53 tables from the actual root `migrations/*.sql`; it records which tables have `ENABLE` plus `FORCE` RLS. This classification is an inventory only; all tenant tables without proven RLS remain open security work.

The proposed per-table privileges, tenant-resolution basis, control-plane restrictions and current-vs-required RLS state are recorded in `evidence/phase1/tenant-table-policy-matrix.json`, validated against all 53 migrated tables. The CI/application role must be a dedicated non-owner, non-superuser role with no `BYPASSRLS`; it receives only required DML on tenant tables, read-only catalogue access, and no DDL or unrestricted deletion. Run RLS probes using that actual role, never migration owner/superuser. Apply `FORCE ROW LEVEL SECURITY` wherever owner bypass would otherwise defeat the guarantee. Tenant context is transaction-local and set from authenticated server context. Missing context, stale pooled context, mismatched tenant, or connection reuse must return no cross-tenant rows and permit no mutation. Pool checkout/reset must prove context cannot leak between requests.

The inventory currently shows only `command_receipts` and `domain_events` have both RLS enabled and forced; the other 51 have no such statements in migrations. The current migrations do not provision or grant a dedicated application role with non-owner/non-superuser/non-`BYPASSRLS` properties. The initial RLS implementation is therefore incomplete for the stated Phase 1 tenant guarantee. Required negative integration cases: role attributes; table grants; every tenant table denies unset context; A cannot read/write B; global catalogue cannot be mutated; control-plane operations cannot be called by app role; connection-pool context does not bleed. CI role provisioning and successful execution are pending. No RLS claim may be based only on a repository mock.
