# Phase 1 tenant isolation and application role contract

**Contract:** `phase1-tenant-isolation-v2`
**Status:** Strict RLS direction owner-approved (approval assumed at user direction, 2026-11-07); table-by-table grant/policy evidence and PostgreSQL role proof remain pending.
**Authority:** ADR-005/022; AUD-004; INV-001; Phase 1 plan WP0.3; Phase 0 migration/role conventions.

Every persisted table must be classified before tenant policy work as one of: `tenant_scoped` (tenant key required, RLS enabled and forced, tenant context set per transaction), `global_catalogue_read_only` (no tenant key; application role SELECT only), or `control_plane_restricted` (explicit operation-specific grants, unavailable to ordinary application queries). No table may remain unclassified. Every `tenant_scoped` table requires both `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY`. `evidence/phase1/tenant-table-inventory.json` classifies all 53 tables from the actual root `migrations/*.sql`; it records which tables have `ENABLE` plus `FORCE` RLS. This classification is an inventory only; all tenant tables without proven RLS remain open security work.

The proposed per-table privileges, tenant-resolution basis, control-plane restrictions and current-vs-required RLS state are recorded in `evidence/phase1/tenant-table-policy-matrix.json`, validated against all 53 migrated tables. `security_attempts` is explicitly `tenant_scoped`: it records only authenticated command authorization denials for which trusted actor and tenant context have already been established. Its INSERT policy must bind `tenant_id` to the server-established transaction-local `app.tenant_id`; its application grant is INSERT only (no SELECT/UPDATE/DELETE). Inserted actor/command attribution is derived or validated against trusted server context; client assertions alone cannot set tenant or actor. A failed insertion cannot authorize a command or create a business receipt. Unauthenticated login/CSRF/authentication attempts are not stored in this table; they use the separate WP5 authentication/security audit path. If tenant context cannot be established, do not insert here. WP1.5 must apply this classification to all tables and revalidate the inventory after migrations: tenant-scoped tables receive ENABLE+FORCE and tenant policies; global catalogues are SELECT-only; control-plane tables receive no ordinary app grant. Preserve append-only behavior: `domain_events`, `command_receipts` and `security_attempts` receive no UPDATE/DELETE grant.

The CI/application role is the matrix-named `symphony_app`: a dedicated non-owner, non-superuser LOGIN role with no `BYPASSRLS`, receiving only matrix-approved privileges and no DDL or unrestricted deletion. Run RLS probes using that actual role, never migration owner/superuser. The local `symphony` database owner is not an acceptable runtime identity and cannot be used as a fallback. CI provisions the ephemeral role using `PHASE1_TEST_ADMIN_DATABASE_URL`, separate from `MIGRATION_TEST_DATABASE_URL` and `PHASE1_TEST_APP_DATABASE_URL`; application migrations never create cluster roles. Tenant context is transaction-local under the single setting name `app.tenant_id`, set via parameterized `set_config('app.tenant_id', tenant_id, true)` from authenticated server context. This name supersedes legacy `app.current_tenant_id` usage in migration 0008; the transition is forward-only. Missing/empty context, stale pooled context, mismatched tenant, or connection reuse must return no cross-tenant rows and permit no mutation. Every tenant query also contains an explicit tenant predicate. Pool reuse tests prove context cannot leak between requests.

The inventory currently shows only `command_receipts` and `domain_events` have both RLS enabled and forced; the other 51 have no such statements in migrations. The current migrations do not provision or grant a dedicated application role with non-owner/non-superuser/non-`BYPASSRLS` properties. The initial RLS implementation is therefore incomplete for the stated Phase 1 tenant guarantee. Required negative integration cases: role attributes; table grants; every tenant table denies unset context; A cannot read/write B; global catalogue cannot be mutated; control-plane operations cannot be called by app role; connection-pool context does not bleed. CI role provisioning and successful execution are pending. No RLS claim may be based only on a repository mock.
