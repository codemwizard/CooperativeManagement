# Phase 1 authorization dependency and revocation contract

**Contract:** `phase1-authorization-capacity-v1`  
**Status:** Authority serialization contract owner-approved (approval assumed at user direction, 2026-11-07); complete dependency inventory and PostgreSQL race proof remain pending.
**Authority:** ADR-008/010/020; INV-001/018/021; `03-specification-delta.md` §§2, 10; Phase 1 WP0.4.

Every allow decision records its complete decision basis. Mutable dependencies to inventory include platform role, appointment and source/current status, capacity grant/revocation, delegation grant/revocation, organization/cohort scope, expiry, tenant membership, person identity/conflict facts, and policy/configuration version. For each dependency, record table/source, mutability, tenant/global scope, transaction read point, lock/version mechanism, change operation that must serialize, and test proving it. Snapshot/immutable inputs state their version and effective-time semantics. No omitted dependency may be treated as immutable by assumption.

Protected mutation authorization and the mutation occur in one PostgreSQL transaction. The selected lock/serialization mechanism must cause the protected command and every relevant revocation/change to form one serial order. If the protected command acquires and validates the authority boundary first, it may commit before revocation; revocation waits. If revocation commits first, a later authorization denies. No command may commit after revocation relying on an unlocked stale authority snapshot. Lock order must be deterministic to prevent deadlock cycles; retry is bounded and uses the same command identity.

The complete eight-class dependency/source-table/change-path inventory and expected both-order test cases are in `evidence/phase1/authority-dependency-inventory.json`. Use the approved authority aggregate/version design: every authority-changing command updates the actor-and-tenant authority aggregate/version in the same transaction. Protected commands obtain a shared lock on that aggregate while evaluating and committing; authority-changing commands obtain an exclusive lock. Use deterministic lock ordering. The WP0 pure model proves both serial outcomes for every mapped dependency class; WP2.4 must prove those orders with PostgreSQL barriers for every actual mutation path, not only capacity rows. History rows for prior findings remain immutable; revocation affects future authority only.
