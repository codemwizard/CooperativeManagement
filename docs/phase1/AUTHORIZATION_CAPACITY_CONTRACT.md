# Phase 1 authorization dependency and revocation contract

**Contract:** `phase1-authorization-capacity-v2`
**Status:** Authority serialization contract owner-approved (approval assumed at user direction, 2026-11-07); complete dependency inventory and PostgreSQL race proof remain pending.
**Authority:** ADR-008/010/020; INV-001/018/021; `03-specification-delta.md` §§2, 10; Phase 1 WP0.4.

Every allow decision records its complete decision basis. The inventory classifies each dependency as actor-tenant, organization, person/shared-identity, global policy/configuration, or immutable/versioned snapshot. Mutable dependencies include platform role, appointment and source/current status, capacity grant/revocation, delegation grant/revocation, organization/cohort scope, expiry, tenant membership, person identity/conflict facts, and policy/configuration version. For each dependency, record authoritative table/source, mutability, scope, transaction read point, lock/version mechanism, every change operation that must serialize, affected command classes, and tests proving both serial orders. Snapshot/immutable inputs state their version and effective-time semantics. No omitted dependency may be treated as immutable by assumption.

Protected mutation authorization and the mutation occur in one PostgreSQL transaction. The selected lock/serialization mechanism must cause the protected command and every relevant revocation/change to form one serial order. If the protected command acquires and validates the authority boundary first, it may commit before revocation; revocation waits. If revocation commits first, a later authorization denies. No command may commit after revocation relying on an unlocked stale authority snapshot. One lock order applies across command-aggregate locks and authority locks: first command aggregate lock (when present), then authority scopes ordered `global-policy`, `organization`, `person/shared-identity`, `tenant`, `actor`; within a scope order by canonical scope key, dependency type, then dependency ID. Every command and mutation path follows that order. A path that cannot determine its complete lock set before acquisition must use a documented retry-safe protocol that cannot acquire a later-order lock and then request an earlier-order lock. Retries are bounded and reuse the same command identity.

The complete dependency/source-table/change-path inventory and expected both-order tests are in `evidence/phase1/authority-dependency-inventory.json`. Retain the actor-tenant authority aggregate/version, but it is not the sole serialization mechanism. Actor-tenant changes update that aggregate in the same transaction. Organization-scoped, person/shared-identity, and global policy/configuration facts use their authoritative row/version or scope lock; each mutation and protected command that depends on the fact participates in the common lock order. A global or multi-organization mutation must lock all affected scopes in sorted order and advance/invalidate every affected actor-tenant aggregate atomically, or serialize on the authoritative global/scope version read by the protected command. Role definitions and global policy may be frozen only when the inventory explicitly states that they are immutable for the whole Phase 1 runtime; otherwise version and lock them. WP0 pure vectors cover both serial orders by dependency class; WP2.4 must prove them with PostgreSQL barriers for every mutation path and multi-dependency operation. History rows for prior findings remain immutable; revocation affects future authority only.
