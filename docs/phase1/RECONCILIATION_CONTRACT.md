# Phase 1 reconciliation inbox contract

**Contract:** `phase1-reconciliation-v1`  
**Status:** Owner-approved minimal contract (approval assumed at user direction, 2026-11-07); role mapping, retention configuration and executable proof remain pending.
**Authority:** Phase 1 remediation plan v2 WP0.2; `03-specification-delta.md` §9; AUD-003; PRV-002/004/005; WP0.1 command transaction contract.

The inbox is a narrow store for accepted stale/conflicting commands only. It is distinct from command receipts, domain events, outbox messages, logs and generic case management. It exists to preserve both attempted inputs needed to reconcile a stale version. Persist only command ID, tenant ID, original actor ID, target/aggregate ID, expected version, observed current version, minimal typed field changes needed to reconcile, created/updated/expiry times, lifecycle, safe reason code and audit metadata. Encrypt every field containing personal or sensitive data using the general `KeyProvider.encrypt/decrypt` operation. Do not use blind-index APIs or store blind-index output here. A receipt may contain an opaque reconciliation ID only.

The original actor may read their record only while current tenant membership and permission remain valid. A currently authorized tenant actor with the explicit `reconciliation.inbox.takeover` capability may take over only with current tenant membership and audited access. Assigning that capability is governed by persisted authority; no client-supplied role/capability is trusted. Unrelated actors and tenants receive a non-disclosing denial. Resolving creates a corrected command under a fresh command ID, independently authorized under current policy; the original command ID remains permanently bound to its terminal stale receipt and is never reused. Lifecycle is `open` → `resolved` or `superseded`.

At expiry, delete encrypted payload from active storage and retain only a non-identifying tombstone/audit fact. No universal numeric duration is approved; expiry is configured from the per-category retention policy, including O-10 exceptions. Do not pick a duration in code or claim deletion from replicas/backups automatically. The isolated local PostgreSQL 18.0 test server was observed with no recovery/streaming replica, no replication slots, and `archive_mode=off`; external backup/snapshot coverage is unknown. This observation is retained in `evidence/phase1/database-capability-check.md` and does not establish restore/backup expiry or crypto-inaccessibility. Before a deployment with replicas/backups or real data, WP3.4 must record its actual retention interval, expiration/restore behavior and key-provider limitations.

Pure access/lifecycle model vectors in `evidence/phase1/reconciliation-contract-vectors.json` now pass for original actor, current membership/permission, `reconciliation.inbox.takeover`, unrelated same-tenant actor, cross-tenant actor, expired/closed items, exact expiry-to-tombstone disposition and fresh corrected-command ID. These do not prove API authorization, PostgreSQL RLS, encryption, durable audit, active-store deletion/tombstone, replica propagation or backup expiry. Those paths are deferred to WP1.4/WP1.5/WP3.2/WP3.4. No generalized case workflow is authorized.
