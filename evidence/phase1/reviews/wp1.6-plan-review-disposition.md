The authoritative graph now has seven WP1.6 technical predecessors: WP1.1–WP1.5, WP2.2, and WP5.3. WP1.7 is removed from that edge because it owns downstream reconciliation-inbox authorization, not command submission. WP2.2 and WP5.3 remain real technical prerequisites and are scheduled before WP1.6; work-package numbers do not establish chronological order. See `Implementation-Plan-V4/implementation/PHASE-1-REMEDIATION-ROADMAP-FROM-WP1.6.md`.

BDD-AUD-016 remains a separate unresolved acceptance-scope conflict: original Phase 6 owns immutable validation runs, but the approved Phase 1 BDD baseline currently assigns it to WP1.6. It is not a technical predecessor to command API composition. WP1.6 implementation can begin after its seven actual technical dependencies and all remaining API contract decisions pass; WP1.6 BDD closeout cannot pass until BDD-AUD-016's scope and executable owner path are resolved. The earlier blanket statement that the entire WP1.6 implementation must not start until that BDD disposition is resolved is superseded. The `occurredAt` owner ruling and API-contract reconciliation remain independent WP1.6 start requirements.
