## Work-package readiness boundaries

- **REM-WP2.1:** Its specification work is ready to schedule because its graph predecessor REM-WP0.4 is closed. Before production policy code, freeze the full action catalogue and typed-parameter matrix, trace each row to requirements/invariants, and implement a completeness verifier that rejects unknown, duplicate, untraced, missing and starter-fixture-only rows. The existing 25-row fixture is not a substitute for the complete policy specification.
- **REM-WP2.2:** Conditional on WP2.1 and its graph predecessors. Before implementation, commit the typed trusted-authority DTO and resolver contract: authenticated actor/tenant, persisted membership and organization identity, applicable appointment/capacity/delegation state, provenance, D-16 scope tuples/versions and transaction time. Define fail-closed behavior for absent, duplicate and contradictory source rows. Do not add person/shared-identity fields absent a frozen Phase 1 rule; retain them in Phase 2.
- **REM-WP2.3:** Conditional on WP2.2 and its graph predecessors. Before implementation, freeze exact grant/revoke command schemas, lifecycle/effective-time semantics, delegation provenance, duplicate/replay outcomes, event/projection identities, atomic receipt/state/event/outbox behavior and every D-16 scope affected by each command.
- **REM-WP2.4:** Not ready for product implementation until WP2.1–WP2.3 pass. Implement the reviewed PostgreSQL migration, RLS/grants, trigger, actual app-role command paths, both barrier-controlled race orders for every supported writer, all frozen-source privilege/registry negative proofs, and rollback/retry evidence. Mocks, one-connection tests, test-owner product operations and sleep-only race tests do not satisfy acceptance.
- **REM-WP2.5:** Acceptance boundary only. Close after WP2.1–WP2.4 pass and WP1.6 proves its real API path; it is not a substitute for either stream's individual evidence.
- **REM-WP5.1:** Ready to schedule when its listed graph prerequisites pass; implement the real shared Fastify API and runtime schemas. Validate request/response contracts at the boundary and prove malformed input and unexpected failures cannot bypass generic error handling.
- **REM-WP5.2–WP5.3:** Schedule only when each task's own graph predecessors pass. D-14 fixes a 12-code-point minimum, 1,024-code-point maximum, Unicode/space passphrases, no composition rules, no normalization/trimming, Argon2id (19 MiB, 2 iterations, parallelism 1, unique salt), and persisted credential/session lifecycle. Rate limiting uses independent 15-minute account and trusted-source windows: first five prior failures have no added delay; subsequent delay steps are 1, 2, 4, 8, 16, then 32 seconds capped; apply the greater independent delay. Each failure expires at 15 minutes, successful auth clears account history only, there is no permanent lockout, and keyed HMAC identities plus shared PostgreSQL reservations prevent multi-instance/concurrent bypass. WP5.3 remains independent of WP2.2. Tests must exercise every threshold, step, cap, exact expiry boundary, reset, provisional-attempt cleanup/crash expiry, parallel requests across independent API instances, generic unknown-account responses and persisted fresh-connection state.
- **REM-WP5.4:** Requires WP5.3 and WP6.1 per the graph. Use the real API, workspace, PostgreSQL and a persisted test user. Prove login/session cookie behavior, non-enumerating failure, forced-password-change routing, revocation of all sessions after password change, fresh login, and accessible validation/error interaction. Mocks, route interception, localStorage bearer injection and static-page evidence cannot pass.
- **REM-WP5.5:** Requires WP5.2, WP5.3 and WP5.4. Execute the exact manifest/map-owned authentication BDD against persisted API/workspace paths; reject missing, duplicate, skipped, pending, undefined or zero-step scenarios; preserve child failure propagation. This focused gate remains distinct from the 41-scenario integrated REM-WP7.2 gate.
- **REM-WP1.6:** Its seven graph predecessors remain unchanged. The new plan does not authorize starting it before those predecessor records pass. REM-WP2.5, WP1.7 and the Phase 6 BDD-AUD-016 implementation are not retroactively made WP1.6 prerequisites.
