## Boundary

The authenticated identity comes only from the current persisted REM-WP5.3 session (`userId`, `tenantId`). These identifiers have separate meanings:

- `tenantId` partitions a tenant's data and authorization boundary. It is not a person, member, or cooperative identifier.
- `userId` identifies the login/authentication principal and persisted session subject. One person may have zero or more linked accounts according to an explicitly approved account lifecycle policy; an account is not itself a membership.
- `person_id` is the stable system identity for a human, including a cooperative member, independent of whether that person has an account. Do not expose it as a public/member number.
- `organization_id` identifies a cooperative or other organization. `organization_memberships` identifies a person's membership in one cooperative, with its own status and effective interval. Membership is distinct from an account, office appointment, and tenant boundary.

An authenticated account must resolve through a persisted, auditable account-person link to the person and current membership/authority context relevant to an operation. A role is authority attached to a scoped relationship: for example, Secretary is a current appointment/position for one organization; internal verifier is an organization-scoped capacity; programme manager is a platform role constrained by persisted programme/cohort scope; Union TA is an institutional role constrained by a current delegation; ordinary member is an active membership. Role grants do not attach globally to `person_id` without scope and time.

REM-WP2.2 resolves and returns typed, versioned **identity, membership and authority facts** from persisted records. It does not return workspace persona labels or navigation instructions. WP6.1 maps approved facts to the corresponding workflow persona and navigation. A **persona** is a product-facing description of the kind of work a user can do in a selected context, including its workflow and navigation. It is neither the authenticated user/account, nor the person's identity, nor an authorization role. The server authorizes each operation from current persisted facts; persona selection is only a UI context selection and grants no authority.

The current BDD-UXW-001 owner map and Feature 10 include nine workflow contexts: Cooperative member, Chairperson, Vice-Chairperson, Secretary, Treasurer, Internal verifier, Programme manager, Union TA, and Self-enroller. The three newly enumerated officer contexts are backed by current appointments to the corresponding position codes. Cooperative member is backed by current membership independently of officer appointment. The persona describes the selected workflow and navigation; the authority facts remain separate and server-derived. Member activity and household data-entry persistence are still capability gaps and are not claimed implemented by the context menu.

The WP2.2 resolver contract must preserve the source references, authority type, organization/institution/cohort scope, effective/revoked/expiry state, provenance and resolution time required by its readiness plan. The WP6.1 workspace projection must have its own versioned typed mapping and return only the selected context's display persona, allowed navigation entries, currently authorized organization/cohort context, and a safe organization display name when an authoritative name is available. It must not return PII or expose arbitrary role/capacity strings. Route/API authorization remains independent and server-side.

## Programme manager projection scope

Owner direction grants programme managers universal projection permission provisionally. Interpret this narrowly as read-only access to cooperative/union/federation organization-level projections and capability gaps. It does not grant member-level PII, household or sensitive data; raw evidence contents; mutation; authority grants/revokes; or TA delegation outside the manager's persisted cohort scope under D-17. For a durable industry-style model, represent access as explicit, auditable relationships/grants from a principal to an organization or group (including a union/federation relationship where authorized), with grantor, basis/agreement reference, permitted data domains/actions, effective interval, revocation, and audit history. Resolve the effective scope at request time and invalidate cached scope when grants change; do not put an expandable cohort snapshot in a long-lived token. ABAC policy attributes and relationship-based grants are established patterns for expressing scope and organizational relationships; this project should implement only the narrow fields its owner-approved requirements need.

## Context selection and failure behavior

- A user can have zero, one or multiple current persona contexts. Zero means the authenticated account has no current linked membership/authority context (for example, pending onboarding, disabled membership, or no active appointment); it does not mean that an ordinary member who has an active membership lacks a persona. An account with active membership receives the Cooperative member context even though member data-entry persistence is still a capability gap.
- One means exactly one active authorized workflow context. Multiple means separate contexts, usually across organizations or distinct duties, each independently derived from current persisted relationships. The user may select among these contexts; each request revalidates the selection server-side.
- Zero contexts yields no persona-specific navigation and no organization identity; it does not default to Secretary or a seed organization.
- WP2.2 returns source authority facts in deterministic order; WP6.1 presents the resulting persona/scope contexts. A selected source-context reference is revalidated against current rows on every server request; the client cannot combine a persona from one context with an organization/cohort from another. WP2.2's DTO must not prescribe navigation.
- Expired, revoked, wrong-tenant, wrong-organization, contradictory or ambiguous source rows fail closed. They produce no selected context and no protected data.
- Effective time is evaluated by the server at request time. The API must not trust a client clock, cached persona, or stale workspace response to establish current authority.
- Organization route IDs identify a requested resource only. The workspace rejects a route context outside the loaded context scope, and the context endpoint derives authority from the session. The current cooperative routes render the authenticated shell/capability surfaces; tenant-specific organization record endpoints are not claimed implemented. Any future data endpoint must validate its organization target server-side and avoid disclosing cross-tenant existence.
- These rules do not activate or claim BDD-UXW-012's broader self-enroller route-exclusion scenario while it remains `@wip`.
