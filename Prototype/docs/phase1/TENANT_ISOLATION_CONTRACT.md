# Phase 1 tenant isolation and application role contract

**Contract:** `phase1-tenant-isolation-v2`
**Status:** Strict RLS direction owner-approved (2026-11-07). WP1.4 verified `symphony_app` against the reconciliation inbox-specific grants and RLS on the isolated local test database. The full 55-table grant/policy rollout, legacy context migration and CI ephemeral-role proof remain WP1.5 work.
**Authority:** ADR-005/022; AUD-004; INV-001; Phase 1 plan WP0.3; Phase 0 migration/role conventions.

Every persisted table must be classified before tenant policy work as one of: `tenant_scoped` (tenant key required, RLS enabled and forced, tenant context set per transaction), `global_catalogue_read_only` (no tenant key; application role SELECT only), or `control_plane_restricted` (explicit operation-specific grants, unavailable to ordinary application queries). No table may remain unclassified. Every `tenant_scoped` table requires both `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY`. The accepted WP0 baseline classified 53 tables. The current root migration catalog through 0012 contains 55 tables: those 53 plus `security_attempts` (0010) and `reconciliation_inbox` (0012). `evidence/phase1/tenant-table-inventory.json` records all 55 tables and distinguishes the security-attempt policy work still pending under WP1.5. This classification is inventory evidence, not proof that the full grants or RLS policy set has shipped.

The per-table privileges, tenant-resolution basis, control-plane restrictions and current-vs-required RLS state are recorded in `evidence/phase1/tenant-table-policy-matrix.json`; it accounts for all 55 current migration tables. `security_attempts` is `tenant_scoped`: it records only authenticated command authorization denials for which trusted actor and tenant context have already been established. Its INSERT policy must bind `tenant_id` to the server-established transaction-local `app.tenant_id`; its application grant is INSERT only (no SELECT/UPDATE/DELETE). Inserted actor/command attribution is derived or validated against trusted server context; client assertions alone cannot set tenant or actor. A failed insertion cannot authorize a command or create a business receipt. Unauthenticated login/CSRF/authentication attempts are not stored in this table; they use the separate WP5 authentication/security audit path. If tenant context cannot be established, do not insert here. WP1.5 must apply this classification to all 55 tables and revalidate the inventory after migrations: tenant-scoped tables receive ENABLE+FORCE and correctly scoped policies; global catalogues are SELECT-only; control-plane tables receive no direct ordinary app table grants. Preserve append-only behavior: `domain_events`, `command_receipts` and `security_attempts` receive no UPDATE/DELETE grant. `reconciliation_inbox` remains SELECT/INSERT/UPDATE only with no DELETE. `event_outbox` remains table-inaccessible to `symphony_app`; WP1.5 must replace WP1.2's direct outbox insert with the matrix-named tenant-checking function interface so accepted command events and outbox rows remain atomic without granting table access.

The application role is the matrix-named `symphony_app`: a dedicated non-owner, non-superuser LOGIN role with no `BYPASSRLS`, receiving only matrix-approved privileges and no DDL or unrestricted deletion. This role is provisioned on the local isolated test database; WP1.4 verified only the inbox-specific access boundary. WP1.5 must prove the complete matrix and CI provisions an ephemeral role using `PHASE1_TEST_ADMIN_DATABASE_URL`, separate from `MIGRATION_TEST_DATABASE_URL` and `PHASE1_TEST_APP_DATABASE_URL`. Application migrations never create cluster roles. The local `symphony` database owner is not an acceptable runtime identity and cannot be used as a fallback. Tenant context is transaction-local under the single setting name `app.tenant_id`, set via parameterized `set_config('app.tenant_id', tenant_id, true)` from authenticated server context. This name supersedes legacy `app.current_tenant_id` usage in migration 0008 and the current WP1.2 adapter; WP1.5 performs the forward-only migration and updates runtime code. Missing/empty context, stale pooled context, mismatched tenant, or connection reuse must return no cross-tenant rows and permit no mutation. Every tenant query also contains an explicit tenant predicate. Pool reuse tests prove context cannot leak between requests.

The current migration catalog has ENABLE+FORCE RLS on `command_receipts`, `domain_events` and `reconciliation_inbox`; the first two still use legacy `app.current_tenant_id` policies, while the inbox uses `app.tenant_id`. Other tenant policies and the full grant matrix remain pending. Root migrations do not create cluster roles; the local `symphony_app` login and its scoped WP1.4 grants were provisioned separately, and CI ephemeral-role setup remains to be implemented and verified. Required negative integration cases: role attributes and memberships; exact table grants; every tenant table denies unset/empty context; A cannot read/write B; global catalogue cannot be mutated; control-plane operations cannot be called by the app role; and connection-pool context does not bleed. No RLS claim may be based only on a repository mock.
